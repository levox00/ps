# Petals Hub: new game UI

Use the user's fork at https://github.com/levox00/silk-windui (branch `silk`), not stock WindUI. Use the original transparent Petals mark at https://github.com/levox00/ps/blob/main/assets/petals-logo-transparent.png as the only reusable image from that repository. Check the fork's current state and APIs before use; preserve unrelated work. Read `references/README-template.md` for the mandatory layout and exact visible English copy.

## Before building

Ask the user, preferably together, for any missing decisions: game name; theme/accent color; whether to use Lucide icons for the other controls; whether they want a character and any character, gender, pose, outfit and visual-direction preferences; whether a petal overlay is wanted; and which gameplay features to implement, including the option to start with UI only. Do not repeat answers already given. Never invent features when the user requests a UI-only foundation. Overview and Settings are mandatory even when no features are requested. Use the user's exact game and branding choices; do not replace Petals Hub with the game name.

## Required structure and behavior

- Window header: show the game name above `Petals Hub`, with the themed logo on the left. In Overview, show `Petals Hub` first and the game underneath; follow the exact ordering and copy in the reference. Always use the Lucide `layout-dashboard` icon for Overview and the Lucide `settings` icon for Settings; follow the user's Lucide preference for other controls.
- Create original visual assets for each new game UI instead of reusing the PetSim background, overlay or other artwork from the user's repository. Ask for the theme color and character preferences; default to a newly generated 2D anime-style character when the user does not request otherwise. Respect a requested male character, another character, a supplied reference, or no character. Generate a coordinated background in the chosen palette with petals and the specified character or character-free composition; keep key details clear behind the content. If an overlay is wanted, generate a separate transparent petal overlay matching the palette and background. Do not use the image repository as the source for either asset.
- Preserve the original Petals logo's design and alpha, changing only its color to match the chosen palette. Use the tinted mark in the window and draggable minimized button. Do not redraw it, add a character to it, change its geometry, or use a different image as the logo unless explicitly requested. Keep backgrounds and overlays clipped inside the UI; keep controls usable with mouse and touch. Use normal WindUI window buttons. The fork is an unbranded, image-free base: supply the generated images and palette in the game-specific script rather than hardcoding them into the library.
- Build `Overview` with distinct, visibly titled WindUI sections in this order: `Petals Hub`, `Show / Hide Hub`, `Community`. Place separate title/description rows inside the sections, exactly as specified in the reference. In particular the first section heading is `Petals Hub`, its first paragraph title is `Game`, and that paragraph description is the game name alone (for example `Blade Ball`); do not put `Petals Hub` as the paragraph title or prefix the value with `Game:`. A paragraph title is not a substitute for a visible section heading. Include actual update details; do not fabricate release notes or premium services.
- Build `Settings` with distinct, visibly titled WindUI sections in order: `Appearance`, `Diagnostics`, `Session`, with the controls nested under their corresponding section headings as detailed in the reference. Keep section headings visibly separate from control labels and sections expanded by default. `Settings` must have independently adjustable Background Image Transparency and UI Surface Transparency. Apply UI transparency hierarchically to the outer panel, feature/section surfaces, selected sidebar tabs, dropdown menus and selectable dropdown items; the panel is most transparent, nested controls less transparent but still adjustable. Preserve readable text and icons. Use the fork's `SetBackgroundImageTransparency` and `SetUITransparency` APIs where available; do not fake dropdown support with a slider that does not affect the actual open menu. Do not add an Interface Theme selector or saved profiles.
- Add Diagnostics with Copy Full Debug Report, Save Debug Report to File and Clear Hub Log, with fallbacks when executor capabilities are missing. Do not leak secrets in diagnostics. Add `Stop and Close Hub` to Settings. The top-right X and this action must invoke the same idempotent full shutdown: stop workers, release connections, cancel owned continuations where applicable and destroy only this hub's GUI. Minimize must not stop the hub.
- F8 and Right Control must toggle visibility and re-center an off-screen window on keyboard-equipped devices. Do not consume keys while typing in a text field or create duplicate hotkey listeners. Keep the minimized button draggable and usable on touch.
- Show the Discord popup on the first execution on the local device only. Use the exact text in the reference. Save a per-hub flag after a successful display through available executor file APIs; if persistence is unavailable, state the limitation and do not claim once-only behavior. The popup must not stop initialization if it fails.
- Use one active instance of the specific hub across re-execution; do not destroy other hubs or unrelated UI. Preserve existing features when updating an existing authorized project.

## Delivery and verification

Implement the requested design and only the approved game features. Validate actual paths, alpha channels and raw URLs; compile Luau and check UI lifecycle, dropdown transparency, cleanup and singleton behavior. Where possible, visually verify desktop and touch layouts; distinguish mocks and compilation from live Roblox/Delta evidence. Follow normal publication permissions and the user's hosting choices. Do not add obfuscation, networking or auto-execute unless requested.
