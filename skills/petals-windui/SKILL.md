# Petals Hub: new game UI

Use the user's fork at https://github.com/levox00/silk-windui (branch `silk`), not stock WindUI. Use the original transparent Petals mark at https://github.com/levox00/ps/blob/main/assets/petals-logo-transparent.png as the only reusable image from that repository. Check the fork's current state and APIs before use; preserve unrelated work. Read `references/README-template.md` for the mandatory layout and exact visible English copy.

## Before building

Ask for the game name and desired main UI color if not already given; an unspecified color requires an explicit question. Ask for gameplay features when unclear, including UI-only as an option, and whether Lucide icons are desired for other controls when relevant. Never repeat an answered question or invent game features. Overview and Settings remain mandatory even without gameplay features.

Background, decorative overlay, logo and character are **independent, enabled defaults**. Unless the user opts out, actually generate or prepare and integrate all four; do not ask for confirmation of defaults or require a reference image. Explicit user choices override defaults independently (including only a subset or none). An omitted asset must not be generated, downloaded as a substitute or inserted as a placeholder. When character details are not specified, invent a suitable 2D-anime character; accept supplied preferences, including gender, outfit and pose, or no character. Honor user-provided references if voluntarily supplied, but never require or assume one. Use the exact game and Petals Hub branding choices.

## Visual style, assets and layering

- Use one cohesive, high-quality 2D anime art direction: clean, well-defined flat shapes, soft coordinated gradients, deliberate shading, and decorative stylized anime petals with consistent silhouettes. Avoid photorealistic or generic petals. Coordinate character, scenery, overlay, logo and UI surfaces through the chosen main color, complementary lighter and darker tones, restrained highlights and harmonious accents. For example, a blue theme uses coordinated blues across background, petals, overlay and logo.
- When enabled, generate a new background and a separate transparent decorative petal overlay for the current UI; do not reuse the PetSim or Fake an Egg backgrounds or overlays. Generate the enabled character, either as part of the background or as a separate layer. The character toggle is independent: if the background is disabled but the character is enabled, use a separate transparent character asset; if the character is disabled, exclude it from every asset. When the logo is enabled, recolor the original transparent Petals mark to the chosen palette while preserving shape, geometry and alpha; do not redraw it. Use it in the window and minimized button. If disabled, omit the mark everywhere and keep the draggable minimized control functional without an image. Only the original Petals logo may be reused from the user's image repository.
- Generate the enabled assets and integrate their actual accessible images into the game-specific UI; descriptions, dead URLs, mockups and placeholders are not completion. Use the image-generation/editing tool or an available suitable asset workflow, preserve transparency for overlays and logo, and validate asset loading. If generation, hosting or executor compatibility prevents integration, report the exact blocker rather than claiming completion. Use the fork as an image-free base; keep assets and theme in the game-specific script.
- Layer back to front: background; UI content (window surfaces, sections, tabs, controls and text); decorative overlay. Position the logo and character appropriately within the composition without covering important controls. Scale and crop the background and character appropriately; clip the background and overlay to the UI bounds. Apply ZIndex or equivalent through the actual hierarchy, accounting for the fork's display and stacking behavior. The top overlay must be non-interactive, must not intercept mouse/touch/keyboard input or obscure readable text and controls, and must remain visually subordinate; allow space for interactions. Remove omitted layers cleanly and preserve ordering of the remaining layers. Verify actual layering, legibility, input and scaling on desktop and touch when possible.

## Required structure and behavior

- Window header: show the game name above `Petals Hub`, with the themed logo on the left when enabled. In Overview, show `Petals Hub` first and the game underneath; follow the exact ordering and copy in the reference. Always use the Lucide `layout-dashboard` icon for Overview and the Lucide `settings` icon for Settings; follow the user's Lucide preference for other controls.
- Build `Overview` with distinct, visibly titled WindUI sections in this order: `Petals Hub`, `Show / Hide Hub`, `Community`. Place separate title/description rows inside the sections, exactly as specified in the reference. In particular the first section heading is `Petals Hub`, its first paragraph title is `Game`, and that paragraph description is the game name alone (for example `Blade Ball`); do not put `Petals Hub` as the paragraph title or prefix the value with `Game:`. A paragraph title is not a substitute for a visible section heading. Under `Latest Update`, always show the actual script version; normally show only the version. Add a short note only for a verified major update such as a newly added event or entirely new feature, not routine changes or a general summary. Use the existing version or establish an initial version for a new script; never invent a version for an existing script or fabricate release notes or premium services.
- Build `Settings` with distinct, visibly titled WindUI sections in order: `Appearance`, `Diagnostics`, `Session`, with the controls nested under their corresponding section headings as detailed in the reference. Keep section headings visibly separate from control labels and sections expanded by default. `Settings` must have independently adjustable Background Image Transparency (when a background is enabled) and UI Surface Transparency; omit the background-specific slider if no background exists. Apply UI transparency hierarchically to the outer panel, feature/section surfaces, selected sidebar tabs, dropdown menus and selectable dropdown items; the panel is most transparent, nested controls less transparent but still adjustable. Preserve readable text and icons. Use the fork's `SetBackgroundImageTransparency` and `SetUITransparency` APIs where available; do not fake dropdown support with a slider that does not affect the actual open menu. Do not add an Interface Theme selector or saved profiles.
- Add Diagnostics with Copy Full Debug Report, Save Debug Report to File and Clear Hub Log, with fallbacks when executor capabilities are missing. Do not leak secrets in diagnostics. Add `Stop and Close Hub` to Settings. The top-right X and this action must invoke the same idempotent full shutdown: stop workers, release connections, cancel owned continuations where applicable and destroy only this hub's GUI. Minimize must not stop the hub.
- F8 and Right Control must toggle visibility and re-center an off-screen window on keyboard-equipped devices. Do not consume keys while typing in a text field or create duplicate hotkey listeners. Keep the minimized button draggable and usable on touch, including when the logo is disabled.
- Show the Discord popup on the first execution on the local device only. Use the exact text in the reference. Save a per-hub flag after a successful display through available executor file APIs; if persistence is unavailable, state the limitation and do not claim once-only behavior. The popup must not stop initialization if it fails.
- Use one active instance of the specific hub across re-execution; do not destroy other hubs or unrelated UI. Preserve existing features when updating an existing authorized project.
